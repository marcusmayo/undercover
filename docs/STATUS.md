# Status

The pilot (`docs/PLAN.md`), the harness (`docs/PLAN_HARNESS.md`) and durable state (`docs/PLAN_DURABLE.md`) are built.

- `backend/`: FastAPI with SQLAlchemy Core: on Supabase (the session pooler, schema `undercover`, at most 4 connections) when `DATABASE_URL` is set, otherwise on SQLite. It is seeded from `data/` (never `data/evals/`) and serves the claims queue, policies with their plan limits, customers' claim history (without personal details), the policy wording, the claims manual, the numbered sections of both, the payout rules (`calculate_payout`, from `backend/payout.py`), the agent's two sets of instructions (`backend/instructions/queue.md` and `claim.md`) and the handlers. It records runs with their to-do list and summary, decisions, payments, sign-offs and the agent's steps, and each claim's run and its thread for the current attempt. It enforces the rules: one run at a time, one decision per claim, a payment only for the approved payout, a payout over $1,000 only after a handler's sign-off, and a claim that fails twice is left for a handler. A repeat of a decision or payment already recorded counts as done; a different one is refused. A sign-off records who and when, puts the claim in progress until it is paid, and is handed to the agent's service once saved. The backend tells the service about each new run; if the service can't be reached, the work waits for it.
- `agent/`: the UnderCover Agent, in four parts. Its tools (`agent/tools.py`) reach everything through the backend's API. The claim agent is a hand-written LangGraph graph (`agent/graph.py`): `agent` and `tools` loop until the decision is recorded, then `pay` pays an approval, after `signoff` waits at `interrupt()` when the backend says the payout needs a sign-off. The graph posts every step to the claim, returns refusals to the model, retries model errors, ends a claim at 30 model calls, and saves its progress after every step with the Postgres checkpointer (in memory without `DATABASE_URL`). Its entry point is `run(claim_id, thread_id)`. Each attempt at a claim has its own thread and its own Langfuse session. A run (`agent/queue.py`) is the queue agent, LangChain's `create_agent`, which lists the waiting claims in its scope, writes a to-do list, hands each claim to `work_claim` (`agent/claim.py`) and finishes with a summary. Its instructions are served by the backend. Its service (`agent/service.py`, port 8002) works runs, picks a claim back up after a sign-off, and carries on what was left (a run that was stopped, a claim stopped partway, a claim signed off while it was away) when it starts and at the start of every run. A claim stopped partway carries on with the same thread and attempt; a claim that fails with an error is released and starts afresh. The default model is `deepseek/deepseek-v4.1-flash` with low reasoning effort, or `MODEL_NAME`.
- `dashboard/`: React in the UnderCover brand, light and dark, refreshing on its own. The queue with a count per state and, above it, the current run: its status, scope, times, to-do list with a chip per item, summary or problem, and Run the queue with the number of claims to work. Each claim in full with its policy, history, decision and reasons, the wording of the policy section, what the agent read, and its steps live while it works, with retries marked (Run agent starts a one-claim run). A payout over $1,000 has Sign off, which signs off only: the claim then shows the handler and the time and "The payment is on its way", then the payment and its time once the agent pays. Both sets of instructions, read only. Views are hash links: `#/`, `#/claims/<id>`, `#/instructions`.
- `e2e/`: Playwright tests of the queue, a decision, the sign-off reaching the agent and the payment after it, the instructions, a run's to-do list and summary and its hand-off to the agent, a claim left for a handler and the sections read. They run their own backend on port 8001 with a fresh SQLite database (`e2e/e2e.db`), a stand-in for the agent's service on port 8003 (`e2e/agent-standin.js`) and the dashboard on port 5174, and play the agents' part through the API, so they never call a model.

Live checks on Supabase (November 27 and 28, 2026, DeepSeek V4.1 Flash): after a reseed, Run the queue with a cap of 5 worked CLM-1013, CLM-1023, CLM-1025, CLM-1019 and CLM-1022 in about six minutes with no failures: two approved and paid ($226.00), one declined, two referred; the other 20 stayed waiting. Run agent on CLM-1003 approved $3,750.00, which waited for a sign-off; signed off on the dashboard, it showed as paid, with the handler and the time, 3.8 seconds later. Its Langfuse session holds two traces: the agent's work before the pause and the payment after it. Supabase showed at most 11 connections from the user postgres. After a reseed, a one-claim run on CLM-1001 whose agent service was killed after three tool calls carried on when the service started again, on the same thread, at attempt 0, with one decision and one payment, and the run finished with a summary of it. The decisions have not been scored against `data/evals/`.

Not built, as the spec says: sign-in, real payments and messages to customers. A handler can only sign off a held payout, not reject it. A claim left for a handler can't yet be worked by hand in the dashboard. There is no tool yet for scoring the agent against `data/evals/`.

## Running it

- `uv sync` and `npm install` once. `.env` must exist: `npm run dev` and `npm run seed` read it. With `DATABASE_URL` in it, everything is on Supabase.
- `npm run seed` rebuilds our tables, on Supabase or in `backend/undercover.db` (or the path in `UNDERCOVER_DB`), and leaves the checkpoints. The backend seeds the database on startup if it is missing. Run it again to put every claim back to waiting.
- `npm run dev` starts the backend on port 8000, the agent's service on port 8002 and the dashboard on http://localhost:5173.
- Start a run with Run the queue on the queue page, or Run agent on a waiting claim. From the command line, with `npm run dev` running: `uv run -m agent --cap 5` or `uv run -m agent CLM-1001`. Both start the run through the backend, which hands it to the agent's service, and print the to-do list as it changes, then the summary.
- If the agent's service stops partway (a crash, Ctrl-C), start it again: it carries on the run and the claim from where they got to.
- `UNDERCOVER_AGENT` sets the address of the agent's service (default `http://127.0.0.1:8002`).
- `npm run check` runs every check, with no network and no `.env`.
